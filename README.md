# Qryptive PQC Scanner — GitHub Action

Find quantum-vulnerable and weak cryptography in your repository: RSA, ECDSA, ECDH, DSA,
Diffie-Hellman, DES and 3DES, RC4, MD5, SHA-1, legacy TLS settings, and the certificates and keys
committed beside your code. The scan runs inside your own GitHub Actions runner. It needs no
Qryptive account and no key.

What leaves your runner depends only on which Qryptive credential you give the action. Read
[what is sent, and when](https://qryptive.ai/privacy/scanner) before you add a key.

## See a result first

- [A scan of a deliberately vulnerable repository](https://github.com/qryptive/pqc-scan-demo/blob/main/expected/RESULT.md): the recorded result, readable without a GitHub sign-in. It shows what findings look like. Signed in, open the [latest run](https://github.com/qryptive/pqc-scan-demo/actions) for its job summary; GitHub hides the summary from signed-out visitors.
- [A scan of a post-quantum repository](https://github.com/qryptive/pqc-scan-clean-example/blob/main/expected/RESULT.md): the same workflow on code that already uses ML-DSA and ML-KEM. It reports no vulnerable cryptography in `src/`, and it still catches the deliberately weak files in `control/`.

Both repositories use the quick-start workflow below. Fork one and run it to see the current
behaviour. Counts can change between releases.

## How long it takes

Measured on 2026-11-15 on a standard GitHub-hosted `ubuntu-latest` runner, whole repository, no
Qryptive key:

| Repository | Files scanned | Job time | Peak memory |
|---|---|---|---|
| Flask | 90 | 26 seconds | 1.2 GB |
| Django | 3,064 | about 6 minutes | 1.3 GB |
| Kubernetes | 21,958 | about 6 minutes | 1.4 GB |

Time depends on the code as well as the file count. Django took longer than Kubernetes despite far
fewer files. The workflow below stops any run at 30 minutes. To scan less, narrow the `paths`
input. Pull requests scan only the changed files, so they are much faster.

## Quick start

Add this file as `.github/workflows/pqc-scan.yml`. It sends nothing to Qryptive, never fails the
build because of findings, and only reads your repository (`contents: read`). Pull requests
into `main` scan the changed files; pushes to `main`, the weekly run and manual runs scan the whole
repository.

The workflow keeps the JSON report (`qryptive-scan-report.json`) as an artifact of the run, named
`qryptive-scan-report`. The report lists file paths, line numbers, algorithm names, severities and one-line
recommendations, as the job summary does, but no source code. GitHub keeps it for 90 days by
default (the repository's retention setting can change that). Anyone
with read access to the repository can download it, so on a public repository anyone signed in to
GitHub can. It stays on GitHub; nothing is sent to Qryptive.

<!-- starter:begin (generated by buildFreeScannerWorkflow({ anonymous: true }) in frontend/src/lib/workflowYaml.js; a frontend test holds this block equal to it) -->
```yaml
name: PQC Vulnerability Scan
# Qryptive PQC scan: finds quantum-vulnerable cryptography. The scan runs in this runner.
# This workflow sets no Qryptive key, so nothing is sent to Qryptive.
# The scan still uses GitHub: checking out code, pulling the scanner image from ghcr.io,
# fetching the pull request base, and writing annotations and the job summary.
# It keeps its JSON report, which lists file paths and findings, as an artifact of the run.
# Anyone with read access to the repository can download it: on a public repository,
# anyone signed in to GitHub.

on:
  push:
    branches: ['main']
  pull_request:
    branches: ['main']
  schedule:
    - cron: '17 6 * * 1'   # weekly whole-repo scan, Mondays 06:17 UTC
  workflow_dispatch:

# One scan per branch at a time: a newer run on the same branch (a push, the weekly or a
# manual run) cancels the one still in progress.
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  pqc-scan:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: PQC Vulnerability Scanner
        uses: qryptive/pqc-scanner-action@v1
        with:
          fail_on_vulnerable: "false"   # set to "true" to fail the build on findings
          severity_threshold: medium
          scan_scope: auto              # changed files on pull requests, the whole repo otherwise
          report_format: json

      - name: Keep the scan report
        if: always() && hashFiles('qryptive-scan-report.json') != ''
        uses: actions/upload-artifact@v4
        with:
          name: qryptive-scan-report
          path: qryptive-scan-report.json
```
<!-- starter:end -->

If your default branch is not `main`, change both `branches:` lines. To generate the file with
your branch and options filled in, use [qryptive.ai/scanner/install](https://qryptive.ai/scanner/install).

Findings appear in the job log, the job summary, the report artifact, and as annotations on the
lines with findings. With `report_format: sarif` the run writes the SARIF file instead of the JSON
report, and the artifact step skips. To fail the build on findings, set
`fail_on_vulnerable: "true"`; `severity_threshold` decides which findings count.

## Credentials (all optional)

You do not need any Qryptive credential to scan. The quick start uses none and works fully. A key only
changes what the run sends to Qryptive, as this table shows.

| Qryptive credential | What the run sends to Qryptive |
|---|---|
| **None** (no `pqc_scanner_key`, no `pqc_api_key`) | **Nothing.** No telemetry, no results, no check-in. |
| **Free scanner key** (`pqc_scanner_key`) | **One check-in per run**: the key, the client kind (`ci`) and, if the image carries one, the scanner version. No code, no file names, no findings. It unlocks nothing: the scan is identical. |
| **Organization API key** (`pqc_api_key`) | **The full finding records**, including the **source lines around each finding**, certificate and key details, dependency names and versions, TLS settings, repository and pull request details and the list of files scanned. Some options send more, such as whole files; the privacy page lists every case. |

When both keys are set, the organization API key is used and no free-key check-in is made. The run
still talks to GitHub and `ghcr.io` (checkout, the scanner image, annotations, the job summary, the report artifact). The
full list, field by field: [qryptive.ai/privacy/scanner](https://qryptive.ai/privacy/scanner).

To check the no-credential row yourself, block `*.qryptive.ai` in your runner's egress policy. The
scan completes.

### Free scanner key (optional)

Skip this unless you want your runs counted against a free Qryptive account. It changes nothing about the scan. Get one at
[qryptive.ai/scanner/get-key](https://qryptive.ai/scanner/get-key) (confirm your email address,
copy the key), add it as the repository secret `QRYPTIVE_SCANNER_KEY`, and add one line to the
step:

```yaml
          pqc_scanner_key: ${{ secrets.QRYPTIVE_SCANNER_KEY }}
```

On a pull request from a fork, GitHub does not pass secrets, so that run behaves exactly like a run
with no key. A failed or rejected check-in prints a warning and the scan runs anyway.

## Outputs and reports

| `report_format` | What the run writes |
|---|---|
| `annotations` (default) | Annotations on the lines with findings, plus the job summary |
| `sarif` | `pqc-results.sarif`, for `github/codeql-action/upload-sarif` (needs `security-events: write`; add `actions: read` on private repositories) |
| `json` | `qryptive-scan-report.json` in the workspace: the run outcome, every file's examination status and every finding at every severity, with its full recommendation (`recommendation`, the first line, up to 500 characters; `null` when there is none). Its path is the `report_path` output. |

The job summary states the run outcome: whether every file was examined, which files were not fully
examined and why (up to 10 named per reason; the JSON report lists them all), and findings by every
severity. A scan that could not examine every file says so instead of reporting a clean result. The
summary shows each recommendation as one short sentence; the JSON report keeps the full text.

## Inputs

| Input | Default | Description |
|---|---|---|
| `paths` | `**/*` | Glob patterns to scan, space-separated. The scanner skips binaries, files over 1 MB and files it has no detector for. |
| `fail_on_vulnerable` | `true` | Fail the build when findings at or above `severity_threshold` are found. |
| `severity_threshold` | `medium` | Minimum severity that counts: `critical`, `high`, `medium`, `low`. |
| `scan_scope` | `changed` | `changed` (files in this push or pull request), `all` (the whole repository), or `auto` (changed files on `pull_request`, the whole repository on every other event, including `pull_request_target`). An unrecognised value scans the whole repository and prints a warning. |
| `baseline_scan` | `true` | Scan the whole repository on the first run even when `scan_scope` is `changed`. Also lets the Qryptive platform periodically request a fresh whole-repository scan (with an organization API key). `false` turns off both. |
| `report_format` | `annotations` | `annotations`, `sarif` or `json` (see above). |
| `pqc_scanner_key` | — | Free scanner key. Ignored when `pqc_api_key` is set. It unlocks nothing: the scan is identical. |
| `pqc_api_key` | — | Organization API key. Sends results to your Qryptive dashboard on plans that include the dashboard. |
| `scan_id` | — | Set automatically by Qryptive platform integrations. |
| `platform_url` | — | Override the Qryptive API base URL, for testing. |

## Outputs

| Output | Description |
|---|---|
| `report_path` | Workspace-relative path of `qryptive-scan-report.json` when `report_format` is `json`. |

## How the action is built

The action is a Docker image (`ghcr.io/qryptive/pqc-scanner:v1`). The scanner inside it is compiled
to a native binary with [Nuitka](https://nuitka.net/), so the image does not contain the scanner's
Python source.

The same image also has a mode for scanning repositories outside CI (on-prem or air-gapped). Ask
[support@qryptive.ai](mailto:support@qryptive.ai).
